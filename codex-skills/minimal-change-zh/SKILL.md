# Minimal Change ZH

这个 skill 用于小功能开发、保守式迭代、兼容性修改和已有系统上的增量开发。目标是在不破坏现有结构和行为预期的前提下，完成稳定、可验证的改动。

## 触发条件

当用户的请求接近以下表达时，使用本 skill：

- “最小改动做这个需求”
- “不要重构”
- “保持现有接口不变”
- “在现有逻辑上加一个功能”
- “只改相关代码，不要扩散”

## 输入检查

开始前优先确认：

- 需求边界是什么
- 哪些接口、行为和结构不能动
- 现有实现在哪些文件
- 是否已有可复用逻辑或测试

如果范围不清，先通过读代码缩小改动面，而不是先设计一套新结构。

## 工作目标

1. 在现有实现上完成需求闭环。
2. 保持接口、结构和已有行为尽量稳定。
3. 把改动限制在真正必要的范围内。
4. 用最小相关验证证明改动成立。

## 标准执行流程

### 1. 理解现有实现

- 阅读相关入口、调用链、数据结构和已有测试。
- 找到最自然、最靠近需求的改动点。
- 优先复用已有逻辑，而不是平地起新层。

### 2. 控制改动范围

优先遵循以下原则：

- 只改与需求直接相关的文件和分支
- 保持现有接口和调用方式不变
- 保持现有代码风格和组织方式
- 非必要不引入新抽象、新依赖、新范式

### 3. 处理分叉方案

如果存在多个可行方案，默认选择：

- 改动最小
- 回归风险最低
- 最容易验证
- 最符合当前项目模式

### 4. 验证与交付

- 改完优先跑最相关的局部验证
- 说明是否保持了原有行为
- 明确未覆盖的边界和后续建议

## 风险边界

- 不顺手清理无关代码。
- 不借需求改动做大规模重构。
- 不在没有必要时扩展接口、重命名大量符号或重排目录结构。
- 如果发现更深层设计问题，先完成当前交付，再单独说明。

## 输出要求

最终汇报优先包含：

1. 需求是怎么落到现有实现上的
2. 为什么选择这个最小改动点
3. 改动是否保持了原有接口和行为
4. 跑了哪些验证
5. 还剩哪些风险或未覆盖场景

## 推荐触发示例

```text
按 minimal-change-zh 做这个需求，先看现有实现，保持整体结构和接口不变，优先最小改动完成，改完跑相关验证，并告诉我为什么选这个改动点。
```
