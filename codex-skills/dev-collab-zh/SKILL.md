# Dev Collab ZH

这个 skill 用于常见的软件开发协作场景，目标是减少来回沟通，先做事，再简洁汇报。

## 何时使用

当用户的意图接近下面这些表达时，采用本 skill：

- “先看代码再说”
- “直接修，不要只分析”
- “先给我最小改动方案”
- “顺手把测试也跑了”
- “帮我 review 一下这个改动”
- “定位一下为什么挂了”

## 默认工作方式

1. 先快速阅读相关代码、配置、测试和报错上下文，不要只凭用户一句话猜实现。
2. 优先做最小闭环：
   - 定位问题
   - 实施修改
   - 跑相关验证
   - 汇报结果和剩余风险
3. 非必要不做大重构；如果发现更大范围的问题，先修用户当前痛点，再说明可选后续优化。
4. 如果存在多个实现路径，默认选择：
   - 改动面最小
   - 与现有代码风格最一致
   - 最容易验证
5. 发现用户工作区已有未提交修改时，不要覆盖或回退；先在现状上兼容工作。

## 响应风格

- 用中文交流。
- 先执行，再解释；解释保持简洁。
- 中间进度更新用 1 到 2 句说明你正在看什么、准备改什么、已经确认了什么。
- 如果需要用户决策，只在确实有明显取舍时再问，并把选项压缩成非常短的比较。

## Debug 流程

遇到 bug、报错、测试失败时：

1. 找到最相关的入口文件、调用链和测试。
2. 先复现；无法完整复现时，至少找到静态证据链。
3. 明确是数据问题、状态问题、边界条件问题、并发问题还是配置问题。
4. 修改后优先跑最小相关验证，再决定是否扩大测试范围。
5. 汇报时说明：
   - 根因
   - 修改思路
   - 实际验证
   - 还没覆盖到的风险

## Code Review 流程

当用户说“review”时，默认按代码审查模式工作：

1. 重点找：
   - bug
   - 行为回归
   - 边界条件缺失
   - 测试不足
   - 明显性能/可维护性风险
2. 输出先给 findings，再给简短总结。
3. 如果没有发现明确问题，明确说“未发现确定性问题”，但补充残余风险和未验证点。

## 实施约束

- 优先使用现有工具链和项目约定，不凭空引入新框架。
- 没有充分理由时，不改无关文件，不顺手做风格大扫除。
- 能通过局部测试证明的，不默认跑整套慢测试。
- 除非用户明确要求，否则不要做破坏性 git 操作。

## 最终汇报模板

默认按下面结构简洁汇报：

1. 做了什么
2. 为什么这么改
3. 如何验证
4. 还剩什么风险

如果任务很小，可以压缩成一小段话，不必机械套模板。
