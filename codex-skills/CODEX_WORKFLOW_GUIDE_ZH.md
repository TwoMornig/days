# Codex Workflow Guide ZH

这份文件用来说明当前目录下每个 skill 的用途、推荐使用方式，以及两个 automation 的真实配置草案。

## Skill 一览

### `prd-dev-zh`

用途：

- 把 PRD 翻译成工程任务
- 分析新功能应该落在哪些模块
- 先出开发方案，再进入实现
- 在实现后补 review 和上线前检查

适合什么时候用：

- 你拿到一个新功能 PRD
- 你不想一上来就写代码
- 你希望先把风险、边界和落点理清
- 你希望 Codex 帮你走完整开发流程

使用 demo：

```text
用 prd-dev-zh 处理这个 PRD。先结合代码库做工程化分析，输出功能落点、影响范围、最小可实现方案、风险点、待确认问题和测试要点。确认后再按最小改动实现。
```

```text
按 prd-dev-zh 看这个新功能需求，先不要写代码，先把它拆成开发方案和验证方案。
```

### `bug-fix-zh`

用途：

- 排查 bug
- 定位报错
- 处理测试失败
- 分析接口异常
- 做最小修复并验证

适合什么时候用：

- 你已经知道“有问题”，但不知道根因
- 你不想自己一层层追调用链
- 你希望修复后顺手验证

使用 demo：

```text
用 bug-fix-zh 看这个报错，先复现并定位根因，再做最小改动修复，改完跑相关验证，最后用中文告诉我根因和残余风险。
```

```text
按 bug-fix-zh 处理这个测试失败，不要重构，优先先把失败闭环修掉。
```

### `review-zh`

用途：

- 审查 PR
- 审查分支改动
- 上线前做风险检查
- 查行为回归和测试缺口

适合什么时候用：

- 你要提交前自查
- 你要看别人改动有没有坑
- 你想让 Codex 像 reviewer 一样思考

使用 demo：

```text
用 review-zh review 这次改动，优先找 bug、行为回归、边界条件问题和测试缺口，不要讲风格建议。
```

```text
按 review-zh 看这个分支，如果没有明确问题，也告诉我还有哪些残余风险。
```

### `minimal-change-zh`

用途：

- 小功能开发
- 保守式迭代
- 兼容现有结构的增量修改
- 不想重构时的需求实现

适合什么时候用：

- 你只想加小功能
- 你不想动太多文件
- 你希望保持接口和结构不变

使用 demo：

```text
按 minimal-change-zh 做这个需求，先看现有实现，在不改整体结构的前提下完成，改完跑相关验证。
```

```text
用 minimal-change-zh 改这个逻辑，保持现有接口不变，不要顺手做重构。
```

## Automation Demo

下面两个 automation 是推荐给你的第一批自动化任务。我已经额外把它们写成可复用的 TOML 草案，放在 `codex-skills/automations/` 目录下，方便你在 IDEA 里直接查看和调整。

### `Weekly Repo Summary automation`

用途：

- 每周自动总结最近一周代码变更
- 帮你快速回顾重点改动
- 提醒高风险模块和测试变化

推荐频率：

- 每周一上午 9 点
- 或每周五下班前

推荐 prompt：

```text
检查当前仓库最近 7 天的重要代码变更，输出中文摘要。重点包括：主要功能改动、潜在高风险改动、测试变化、最近变化频繁的模块。结果保持简洁，优先帮助开发者快速判断哪里值得关注。
```

使用效果示例：

- 本周主要变更集中在登录、支付、订单模块
- 支付模块修改了重试逻辑，风险较高
- 登录模块新增校验，但测试覆盖偏少
- 订单模块主要是整理代码，未见明确行为变化证据

对应配置草案：

- [weekly-repo-summary.toml](/Users/dmoon/IdeaProjects/days/codex-skills/automations/weekly-repo-summary.toml)

### `Daily Failure Check automation`

用途：

- 每天自动检查失败项
- 帮你快速发现最值得优先处理的问题
- 适合 CI、测试、构建失败汇总

推荐频率：

- 每天上午 10 点
- 或每天开始工作后的固定时间

推荐 prompt：

```text
检查当前项目最近的失败信息或失败线索，优先关注测试失败、构建失败、明显报错和高影响问题。输出中文摘要，并按优先级列出最值得先处理的 3 个问题；如果当前没有足够信息可判断，也请明确说明缺少什么。
```

使用效果示例：

- 最高优先级：支付模块测试失败，疑似空值边界未处理
- 第二优先级：登录构建警告升级为错误，影响主分支合并
- 第三优先级：订单模块有间歇性失败，需要进一步复现

对应配置草案：

- [daily-failure-check.toml](/Users/dmoon/IdeaProjects/days/codex-skills/automations/daily-failure-check.toml)

## 怎么根据自己的习惯生成 Skill

可以，直接写中文就可以。Skill 本质上就是一个 `SKILL.md` 文件，不要求你一定用英文。对你来说，先把中文写顺比追求术语更重要。

最简单的写法就是三段：

1. 这是什么 skill
2. 什么时候用
3. 用了以后按什么方式工作

你可以直接按这个模板写：

```md
---
name: 你的-skill-名字
description: 当用户想做什么事情、希望你按什么风格工作时，使用这个 skill。
---

# 你的 Skill 名字

## 何时使用

- 场景 1
- 场景 2
- 场景 3

## 默认工作流

1. 第一步做什么
2. 第二步做什么
3. 第三步做什么

## 约束

- 不要做什么
- 优先做什么
- 最终怎么汇报
```

## 怎么从自己的习惯提炼 Skill

你只要回想自己平时最常说的 3 类话：

- 你总让 Codex 先做什么
- 你总强调不要做什么
- 你总希望最后输出什么

把这三类写下来，就能变成一个 skill。

例如：

如果你平时总说：

- “先看代码再动手”
- “最小改动”
- “不要重构”
- “改完跑测试”
- “中文汇报”

那你就已经有一个 skill 的雏形了。

## 一个判断标准

如果一类要求你已经重复说了 5 次以上，就值得做成 skill。

最适合先做成 skill 的通常是：

- bug 修复
- code review
- 最小改动开发
- 项目结构分析
- 日志排查

## 推荐做法

- 一开始先用中文写，越短越好
- 每个 skill 只管一种任务类型
- 先让它能稳定工作，再慢慢补细节
- 不要一开始写成“大而全总说明书”

## 什么时候从“普通 skill”升级成“团队 SOP skill”

当你发现下面任意一类情况频繁出现，就值得升级：

- 你总在重复补充同样的边界要求
- 你希望输出格式稳定
- 你想减少 AI 在任务里的自由发挥
- 你已经知道这一类任务的固定流程

团队 SOP 版 skill 往往会多出这些部分：

- 输入检查
- 标准执行流程
- 风险边界
- 输出要求
- 推荐触发示例

这次升级后的 3 个 skill，基本就是按这个结构整理的。

## `prd-dev-zh` 推荐使用方式

这个 skill 最适合拿到新功能 PRD 时使用。推荐按 4 段来触发，而不是一句“直接做”。

### 阶段 1：PRD 分析

```text
用 prd-dev-zh 处理这个 PRD。先不要写代码，先结合当前代码库输出：
1. 功能落点
2. 影响范围
3. 最小可实现闭环
4. 风险点
5. 待确认问题
6. 测试要点
```

### 阶段 2：开发方案

```text
基于刚才的分析，继续按 prd-dev-zh 给我一个最小改动开发方案。要求按“改动点、实现顺序、验证方案”组织，优先复用现有逻辑，不要大重构。
```

### 阶段 3：开始实现

```text
按刚才的方案直接实现，继续按 prd-dev-zh 的方式工作。先看相关代码再动手，优先最小改动，改完跑相关验证。
```

### 阶段 4：实现后检查

```text
现在先不要继续扩展功能，按 prd-dev-zh 从 review 和上线前检查角度再过一遍。重点看行为回归、边界条件、权限风险、测试缺口和明显性能风险。
```
