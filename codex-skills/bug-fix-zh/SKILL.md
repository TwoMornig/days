# Bug Fix ZH

这个 skill 用于 bug、异常、测试失败、接口报错、线上问题排查等场景。目标不是“猜原因”，而是尽可能建立证据链，完成最小修复闭环。

## 触发条件

当用户的请求接近以下表达时，使用本 skill：

- “帮我定位这个报错”
- “这个 bug 直接修一下”
- “先复现，再找根因”
- “测试为什么挂了”
- “这个接口为什么 500”
- “这个线上问题先查原因”

## 输入检查

开始前优先确认以下信息是否可获得：

- 报错文本、日志、失败测试或复现现象
- 相关入口文件、调用链或模块范围
- 当前是否已有未提交修改
- 是否存在用户明确限制，例如“不要重构”“只做最小改动”

如果信息不足，不要停留在抽象分析；先从代码、测试、日志和调用路径里补上下文。

## 工作目标

1. 找到最可能的真实根因，而不是表面症状。
2. 在最小改动范围内修复问题。
3. 尽可能用测试、命令、日志或静态证据证明修复有效。
4. 明确残余风险和未验证部分。

## 标准执行流程

### 1. 建立上下文

- 阅读相关代码、配置、测试和报错信息。
- 确定入口、调用链、状态流转和异常传播路径。
- 如存在多个嫌疑点，先按影响面和证据强度排序。

### 2. 复现或构建证据链

- 能复现时，优先复现并记录触发条件。
- 不能完整复现时，通过以下方式补证据：
  - 失败测试
  - 调用链静态分析
  - 参数流向
  - 日志和错误分支
  - 最近相关改动

### 3. 判断根因类别

优先归类问题类型，避免混乱修复：

- 数据不符合预期
- 状态管理错误
- 边界条件遗漏
- 配置或环境不一致
- 并发、时序或生命周期问题
- 错误处理缺失

### 4. 设计修复方案

默认优先选择以下方案：

- 改动范围最小
- 最符合当前代码风格
- 最容易验证
- 不引入新的不确定性

如果发现更大结构问题，先完成当前问题闭环，再把结构优化作为后续建议，而不是顺手扩散改动。

### 5. 实施与验证

- 只修改与根因直接相关的代码。
- 优先补或更新最相关的测试。
- 优先做最小相关验证，再决定是否扩大验证范围。
- 如果验证失败，继续沿证据链迭代，不要把未证实方案包装成结论。

## 风险边界

- 不覆盖、回退或破坏用户已有未提交修改。
- 不把“可能是”表述成“已经确认”。
- 不为了一次性修干净而做无关重构。
- 不默认扩大到全仓库大扫除或风格清理。

## 输出要求

最终汇报优先包含以下内容：

1. 根因：一句话讲清问题为什么发生。
2. 修改：说明改了什么、为什么选这里改。
3. 验证：列出跑了什么验证、结果如何。
4. 风险：说明还没覆盖到的边界或依赖条件。

如果任务很小，可以压缩表达，但仍要覆盖以上四点。

## 推荐触发示例

```text
用 bug-fix-zh 处理这个报错，先复现并建立证据链，再定位根因并做最小改动修复，改完跑相关验证，最后用中文告诉我根因、修改点、验证结果和残余风险。
```
