# Review ZH

这个 skill 用于 PR review、提交前自查、分支风险检查和改动质量审视。核心目标是发现真实风险，而不是给泛泛而谈的风格建议。

## 触发条件

当用户的请求接近以下表达时，使用本 skill：

- “review 一下这个改动”
- “帮我看这个分支有没有坑”
- “优先找 bug 和回归风险”
- “不要讲风格建议”
- “上线前帮我扫一遍风险”

## 输入检查

开始前优先获取：

- 改动范围
- 相关文件和调用链
- 现有测试或缺失测试线索
- 用户是否强调关注点，例如性能、回归、兼容性或测试覆盖

如果无法看到完整上下文，至少要明确本次 review 的可见范围和盲区。

## 审查目标

1. 识别会导致错误行为、线上事故或后续维护成本上升的问题。
2. 区分确定性问题、高风险推断和普通建议。
3. 输出可执行、可定位、可验证的 findings。

## 标准执行流程

### 1. 理解改动意图

- 先看改动内容，再看相关上下文。
- 判断这次修改想解决什么问题、改变什么行为、依赖哪些前提。

### 2. 进行风险扫描

优先从以下维度检查：

- 正确性：是否会产生错误结果或错误状态
- 回归风险：是否影响原有正常路径
- 边界条件：空值、重复提交、异常分支、并发时序等
- 测试覆盖：关键行为是否被证明
- 维护风险：是否引入脆弱耦合或难以理解的分支

### 3. 形成 findings

每个 finding 尽量包含：

- 问题点
- 触发条件
- 影响范围
- 为什么这是风险

### 4. 区分结论强度

- 确定性问题：有明确证据支持，应优先报告
- 高风险推断：证据较强但未完全验证，可以说明依据
- 一般建议：只有在前两类较少时再简短补充

## 审查边界

- 不把代码风格偏好包装成缺陷。
- 不为了显得“有收获”而制造无关建议。
- 如果没有发现确定性问题，要明确说明，而不是勉强挑毛病。
- 不因为局部写法不喜欢，就忽视真实行为风险。

## 输出要求

输出顺序默认如下：

1. Findings：按严重程度排序。
2. Open Questions / Assumptions：说明 review 盲区或需确认点。
3. Brief Summary：一句到几句简短总结。

如果没有 findings，要明确写“未发现确定性问题”，并补充残余风险或未验证区域。

## 推荐触发示例

```text
用 review-zh review 这次改动，优先找 bug、行为回归、边界条件问题和测试缺口。先给 findings，不要讲风格建议；如果没有明确问题，也告诉我残余风险和未验证点。
```
