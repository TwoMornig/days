# PRD Dev ZH

这个 skill 用于“新功能开发”场景，目标不是拿到 PRD 就直接写代码，而是先把需求翻译成工程任务，再按最小可落地路径实现、验证和收尾。

## 触发条件

当用户的请求接近以下表达时，使用本 skill：

- “这是 PRD，帮我做开发方案”
- “先看看这个新功能怎么落地”
- “结合代码库分析这个需求”
- “先别写代码，先拆方案”
- “从 PRD 到开发怎么做”

## 输入检查

开始前优先确认以下信息是否可获得：

- PRD、需求描述、页面说明或流程说明
- 当前代码库中可能相关的模块或页面
- 用户是否要求最小改动、是否允许改接口/表结构
- 是否已有类似功能可以复用
- 是否有时间、范围、兼容性方面的限制

如果需求信息不完整，先基于现有资料做代码对位和风险识别，再把待确认项单独列出来。

## 工作目标

1. 把产品语言翻译成工程语言。
2. 找到功能在现有代码库里的落点和影响范围。
3. 设计最小可实现闭环，而不是一上来做大而全版本。
4. 在实现前明确风险点、待确认问题和测试要点。
5. 在实现后补上 review 和上线前检查。

## 标准执行流程

### 1. 读 PRD，转成工程视角

- 提炼功能目标、用户入口、主流程和异常流程。
- 明确输入、输出、状态变化、权限要求和边界条件。
- 把模糊描述转换成可实现问题。

这一阶段优先输出：

- 功能落点
- 影响范围
- 最小闭环
- 风险点
- 待确认问题
- 测试要点

### 2. 对位现有代码库

- 找到最相关的模块、页面、接口、数据结构和相似实现。
- 优先复用已有能力，而不是假设需要新建一整套逻辑。
- 判断本次改动最可能落在哪几层，例如前端、接口、服务层、数据层。

### 3. 给出最小实现方案

默认优先以下原则：

- 改动最小
- 最符合现有结构
- 最容易验证
- 最容易 review 和回滚

输出时优先按以下结构组织：

1. 改动点
2. 实现顺序
3. 验证方案

### 4. 进入实现

- 先看相关代码再动手。
- 优先复用现有模块、接口和测试。
- 不顺手做大重构，除非用户明确要求。
- 开发过程中持续做局部验证，而不是全部写完再看。

### 5. 实现后 review

实现完成后，不要立即结束，至少补一轮风险检查，优先看：

- 行为回归
- 边界条件
- 权限问题
- 测试缺口
- 性能和稳定性风险

### 6. 上线前检查

最后再过一遍：

- 是否影响旧逻辑
- 错误处理是否完整
- 是否缺少日志、监控或审计信息
- 是否存在兼容性和配置风险

## 风险边界

- 不把模糊 PRD 直接当成完全明确的工程需求。
- 不因为是“新功能”就顺手重构无关模块。
- 不跳过待确认项，直接擅自决定高风险行为。
- 不只关注主流程，忽略权限、失败路径和回归范围。

## 输出要求

默认按以下阶段输出：

1. PRD 分析
2. 开发方案
3. 实现结果
4. Review 结论
5. 上线前检查

如果用户只要其中某一阶段，可以只输出对应部分。

## 推荐触发示例

```text
用 prd-dev-zh 处理这个 PRD。先结合代码库做工程化分析，输出功能落点、影响范围、最小可实现方案、风险点、待确认问题和测试要点。确认后再按最小改动实现，改完做 review 和上线前检查。
```
